## 1. Попередня робоча назва проєкту

**Українською:** «Проєктування та розробка системи автоматизованого сценарного тестування REST API з аналізом результатів».

**Англійською:** «Design and Development of an Automated Scenario-Based REST API Testing System with Results Analysis».

## 2. Актуальність та проблематика

Перевірка REST API є складовою забезпечення якості програмного забезпечення. Під час ручного тестування фахівець повторює HTTP-запити, порівнює фактичні відповіді з очікуваними результатами та документує виявлені відхилення. Такий підхід потребує значних повторюваних зусиль, особливо за регулярних змін програмного інтерфейсу.

Окремою інженерною проблемою є тестування взаємозалежних операцій. Наприклад, ідентифікатор ресурсу, створеного запитом POST, необхідно передати до наступного запиту GET, після чого перевірити статус відповіді та значення полів JSON. Ручне передавання цих даних ускладнює відтворення сценарію, пошук причин помилок і порівняння результатів різних запусків.

Мета проєкту — спроєктувати та реалізувати програмну систему, яка дає змогу описувати багатокрокові сценарії перевірки REST API, автоматично виконувати їх, перевіряти результати за визначеними критеріями та зберігати історію запусків для подальшого аналізу. Інженерна цінність полягає насамперед у механізмі виконання сценаріїв і перевірки результатів, а не лише в операціях створення та редагування записів.

## 3. Сформована ідея продукту та архітектура

Пропонується розробити веборієнтовану систему автоматизованого сценарного тестування REST API з **модульною монолітною архітектурою**. В одному застосунку з чітко розмежованими компонентами реалізовуватимуться керування сценаріями, їх виконання, перевірка відповідей і збереження результатів. Це дає змогу зосередитися на логіці тестування без розгортання мікросервісів, брокерів повідомлень або розподілених обчислень.

Логічна структура системи:

- **Вебінтерфейс (Blazor):** налаштування сценаріїв і запитів, запуск перевірок, перегляд історії та звітів.
- **Керування сценаріями (ASP.NET Core):** збереження сценаріїв, впорядкованих кроків, параметрів запитів, правил перевірки й іменованих змінних.
- **Механізм виконання:** послідовні кроки з асинхронними HTTP-викликами через `HttpClient`, отримання значень із відповідей і їх підстановка в наступні запити.
- **Модуль перевірок:** зіставлення HTTP-статусів, значень визначених JSON-полів та часу відповіді із заданими критеріями.
- **Збереження та звітність:** запис історії запусків і результатів кроків до PostgreSQL через Entity Framework Core; відображення короткого підсумку та звіту за окремим запуском у вебінтерфейсі.

Основний сценарій: користувач створює послідовність HTTP-запитів → система виконує запит → вилучає потрібне значення з JSON-відповіді → підставляє його в наступний крок → перевіряє відповіді → зберігає результати й відображає звіт. Наприклад, ідентифікатор, повернений запитом POST, автоматично використовується у наступному GET.

**Межі реалізації:** кроки виконуються послідовно, без фонових черг; для отримання значень із JSON передбачено лише прості шляхи до вкладених властивостей (наприклад, `data.id`), а не повний JSONPath. Не передбачено довільних користувацьких скриптів, CSV-експорту звітів, складної аналітики чи графічних панелей моніторингу.

**Базові вимоги до безпеки й надійності:** перевірка введених даних, таймаути HTTP-запитів, обмеження кількості кроків і розміру відповідей, контрольована обробка мережевих помилок та невалідного JSON. Для зниження ризику SSRF застосовуватиметься перелік дозволених тестових адрес, обмеження доступу до службових і внутрішніх адрес та заборона автоматичних перенаправлень; доступ до локального тестового API налаштовуватиметься явно лише у довіреному середовищі. Секрети не повинні записуватися до історії, журналів або звітів у відкритому вигляді. Ці положення визначають мінімальну якість майбутнього продукту, а не окремі великі підсистеми чи вже реалізовані можливості.

## 4. Основні функціональні можливості (Core Features)

1. **Керування тестовими сценаріями та HTTP-запитами.** Створення, редагування, збереження та видалення сценаріїв із впорядкованими кроками; налаштування методів GET, POST, PUT, PATCH і DELETE, URL, заголовків, параметрів та тіла запиту.
2. **Автоматизоване сценарне виконання.** Послідовне виконання взаємозалежних запитів, вилучення визначених значень із JSON-відповідей і передавання їх до наступних кроків через іменовані змінні. HTTP-операції виконуються асинхронно з таймаутами та контрольованою обробкою помилок.
3. **Перевірка результатів HTTP-запитів.** Порівняння фактичного HTTP-статусу, значень вибраних JSON-полів і тривалості відповіді із заданими критеріями; фіксація успішних і невдалих перевірок.
4. **Збереження історії тестування.** Збереження часу запуску, підсумкового стану сценарію, результатів кроків і перевірок та тривалості виконання у PostgreSQL.
5. **Аналіз результатів і формування звітів.** Перегляд у вебінтерфейсі підсумку запуску, кількості успішних і невдалих перевірок, часу виконання та деталізованих результатів кожного кроку без окремого експорту файлів.

## 5. Попередній інструментарій та технологічний стек

**Мінімальний стек для реалізації:**

- **Мова програмування і платформа:** C#, .NET.
- **Серверна частина:** ASP.NET Core, `HttpClient` / `IHttpClientFactory`, вбудовані Dependency Injection та `async/await`.
- **Вебінтерфейс:** Blazor.
- **Архітектура:** модульний моноліт, розмежування відповідальності між компонентами та інтерфейси для перевірки логіки.
- **База даних:** PostgreSQL, Entity Framework Core, міграції схеми.
- **Тестування:** xUnit для логіки сценаріїв і перевірок; інтеграційні тести основного процесу виконання.
- **Контроль версій і Docs-as-Code:** Git, GitHub, Markdown-документація у каталозі `/docs`.

**Додаткові інструменти за потреби, без зобов'язання застосовувати всі:** Docker — для зручного локального запуску PostgreSQL; GitHub Actions — для простого автоматичного збирання й запуску тестів; Swagger/OpenAPI — лише якщо для системи буде виділено публічні HTTP-ендпоїнти. Вони не є окремими функціями майбутнього застосунку. Брокери повідомлень, Kubernetes, мікросервіси та спеціалізована платформа моніторингу не плануються.

**Критерій перевірки майбутньої реалізації:** модульні та інтеграційні тести, зокрема сценарій «POST → вилучення ідентифікатора → GET → перевірки → збереження історії → перегляд звіту». Негативні перевірки мають охоплювати таймаут, недоступний сервер, відсутнє JSON-поле, недопустиму адресу та відсутність секретів у результатах. Наявність фактичних результатів тестів підтверджуватиметься лише після створення й запуску програмного коду.

Технологічний стек і межі реалізації є попередніми та підлягають остаточному уточненню з науковим керівником.
