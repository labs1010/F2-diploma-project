# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.1. Актуальність вибраної теми дослідження

Тестування REST API передбачає багаторазове виконання HTTP-запитів, зіставлення фактичних відповідей з очікуваними результатами та фіксацію відхилень. За ручного виконання цих операцій повторні перевірки після змін програмного інтерфейсу потребують відтворення однакових дій. Відсутність формалізованого опису кроків і єдиної історії запусків ускладнює простежуваність та порівняння результатів тестування.

Особливої уваги потребують сценарії з взаємозалежними REST API-операціями, коли значення з JSON-відповіді одного запиту використовується в наступному. Наприклад, після створення ресурсу запитом POST його ідентифікатор необхідно передати до GET, перевірити HTTP-статус, поля JSON і тривалість відповіді та зафіксувати результати кожного кроку. Проєктування механізму послідовного виконання таких сценаріїв, контрольованої обробки помилок і збереження історії є актуальним інженерним завданням. Кількісні переваги запропонованого рішення підлягатимуть оцінюванню лише після реалізації та випробувань.

Предметну постановку уточнено до тестування залежних REST API-операцій, для яких результат попереднього кроку впливає на формування наступного запиту. У цьому випадку необхідно поєднати опис сценарію, алгоритм послідовного виконання, правила перевірки відповідей та ідентифіковані результати окремих запусків. Вимога простежуваності означає можливість пов'язати зафіксовану невдалу перевірку з конкретним кроком, очікуваним критерієм і отриманою відповіддю або мережевою помилкою. Під час розроблення передбачається перевірити доцільність такого підходу на відтворюваному сценарії створення й отримання ресурсу.

Проблема розглядається у межах інженерії якості програмного забезпечення. Не припускається, що наявні універсальні API-клієнти не вміють автоматизувати сценарії; обґрунтуванню підлягає цілісна навчально-практична реалізація обмеженого механізму виконання, верифікації та збереження історії із чітко визначеними критеріями перевірки.

## 1.2. Огляд сучасних підходів до вирішення відповідних завдань в межах обраного дослідження

**Сценарне тестування на рівні HTTP.** REST API перевіряється через формування запитів із відповідними HTTP-методами, адресами, заголовками, параметрами та, за потреби, тілом. RFC 9110 визначає семантику методів і статусів HTTP; тому перевірка лише успішності транспортного з'єднання недостатня: отриманий статус необхідно зіставити з очікуваним результатом операції [H1]. Для даних формату JSON зміст відповіді інтерпретується відповідно до RFC 8259, що відокремлює коректність синтаксису JSON від правильності конкретних прикладних значень [H2].

**Організація залежних операцій.** У сценаріях створення й подальшого читання ресурсу значення `id`, одержане після `POST`, використовується в адресі наступного `GET`. Реалізувати такий зв'язок можна ручним копіюванням, змінними середовища в API-клієнті або окремим виконуваним механізмом, що підтримує спільний контекст поточного запуску. Для предмета дослідження обрано послідовну інтерпретацію впорядкованих HTTP-кроків: на кожному кроці визначаються вхідні параметри, формується запит, обробляється відповідь, зберігаються дозволені значення та виконуються передбачені перевірки. Простий шлях на зразок `data.id` обмежує область вилучення JSON-полів; повний JSONPath і довільні скрипти не є необхідними.

**Формалізація перевірок.** Підхід assertions передбачає порівняння фактичного значення з явно заданим очікуваним: коду HTTP-статусу, окремого поля JSON або максимально дозволеного часу відповіді. Результат перевірки повинен містити ідентифікатор правила, факт виконання й діагностичну причину відхилення. Час відповіді залежить від зовнішнього API та мережі, тому ця величина характеризує тестований сервіс у відповідному запуску, а не продуктивність вебінтерфейсу власної системи. Продуктивність власного застосунку оцінюватиметься окремими метриками.

**Виконання та накопичення результатів.** Наявні API-клієнти підтримують колекції, змінні, скрипти й/або командне виконання; конкретні можливості Postman, Insomnia та Bruno предметно досліджено у підрозділі 1.3. Для запропонованої системи достатньо запуску сценарію на запит користувача, отримання результатів кроків та збереження стислої історії у реляційній базі даних. Асинхронні HTTP-виклики через `HttpClient` та `IHttpClientFactory` забезпечують основу керування HTTP-клієнтами й обробкою їхнього життєвого циклу, але самі собою не гарантують безпеки адрес, коректності перевірок або результатів тестування [M1].

**Безпека виконання тестових запитів.** Оскільки система приймає адреси викликів від користувача, доступ до небажаних внутрішніх ресурсів є ризиком SSRF. OWASP рекомендує визначати довірені призначення, перевіряти адреси, враховувати DNS-перетворення та обмежувати перенаправлення [S1, S2]. Для локального дипломного прототипу передбачається невеликий перелік дозволених тестових призначень, перевірка фактичної мережевої адреси перед з'єднанням, вимкнення автоматичних редиректів і явна окрема конфігурація довіреного локального API. Такий підхід є обмеженням конфігурації, а не додатковою бізнес-функцією; OAuth2/OIDC, хмарна оркестрація й мікросервісна інфраструктура не випливають із поставленої задачі.

**Технічні джерела:** [H1] https://www.rfc-editor.org/rfc/rfc9110.html; [H2] https://www.rfc-editor.org/rfc/rfc8259.html; [M1] https://learn.microsoft.com/en-us/aspnet/core/fundamentals/http-requests?view=aspnetcore-10.0; [S1] https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html; [S2] https://api-security.owasp.org/editions/2023/en/0xa7-server-side-request-forgery/. Дата звернення: 11.11.2026.

## 1.3. Аналіз та порівняння існуючих рішень на ринку готових програмних продуктів

**Дата перевірки відкритих джерел:** 11 листопада 2026 року. **Предмет зіставлення:** програмні засоби для конструювання, виконання й перевірки сценаріїв REST API. Для порівняння обрано Postman, Insomnia та Bruno як реальні аналоги з документованими механізмами HTTP-запитів, тестових сценаріїв і автоматизації. Власна система перебуває **на етапі проєктування**; відомості про її можливості нижче означають *передбачено проєктом*, а не виконану реалізацію.

**Правило доказовості.** Твердження про можливості клієнта, формат файлів або API/CLI спираються на документацію виробника чи відкритий репозиторій. Внутрішні сервіси, СУБД, способи реплікації, гарантовані RPS, Latency та Fault Tolerance не виводяться з назви продукту або з наявності клієнтської функції. Відсутність відкритих характеристик позначається як невизначеність джерел, а не як дефект аналога.

### 1.3.1 Postman

**Призначення й архітектура.** Postman надає клієнтське середовище для формування API-запитів, організації їх у колекції та запуску перевірок. Документовані desktop-клієнт і хмарні робочі простори, а також локальний *lightweight API client*, який працює без входу до облікового запису та не синхронізує власні дані з Postman Cloud. Таке розділення дає вибір між локальною роботою та спільним хмарним контуром. Конкретну внутрішню серверну архітектуру, тип промислової СУБД та схему консистентності даних Postman Cloud цими матеріалами **не підтверджено**. Джерела: [P1](https://learning.postman.com/docs/getting-started/basics/using-api-client), [P5](https://learning.postman.com/docs/getting-started/basics/syncing).

**Протоколи та HTTP-взаємодія.** Для сценарного тестування доступні HTTP-запити; Collection Runner також документує запуск GraphQL і gRPC. У Postman CLI для GraphQL/gRPC зазначено обмеження на unary-виклики, а запуск таких колекцій залежить від тарифного плану. Це можливості тестового клієнта, а не докази використання відповідних протоколів у внутрішніх сервісах Postman. Джерела: [P2](https://learning.postman.com/docs/tests-and-scripts/running-collections/intro-to-collection-runs), [P6](https://learning.postman.com/docs/postman-cli/postman-cli-run-collection).

**Сценарне виконання та перевірки.** Collection Runner запускає впорядковані запити, реєструє результати тестів та виконує JavaScript-скрипти перед/після запиту. Змінні середовища й колекції та post-response scripts дають змогу переносити значення відповіді між кроками; через `pm.test` і `pm.expect` перевіряються HTTP-статуси, JSON-дані та тривалість відповіді. Postman CLI надає командне виконання колекцій для CI/CD. Джерела: [P2](https://learning.postman.com/docs/tests-and-scripts/running-collections/intro-to-collection-runs), [P3](https://learning.postman.com/docs/tests-and-scripts/write-scripts/test-scripts), [P4](https://learning.postman.com/docs/tests-and-scripts/write-scripts/test-examples/), [P6](https://learning.postman.com/docs/postman-cli/postman-cli-run-collection).

**Дані та результати.** Дані lightweight-клієнта залишаються локальними; робочі ресурси звичайного Postman можуть синхронізуватися з Postman Cloud. Офіційно описано керування конфліктами синхронізації. Collection Runner формує результати запуску, однак збереження повних тіл запитів/відповідей має обмеження сесії та розміру; самі журнали запусків не слід ототожнювати з внутрішньою СУБД хмарного сервісу. Джерела: [P1](https://learning.postman.com/docs/getting-started/basics/using-api-client), [P2](https://learning.postman.com/docs/tests-and-scripts/running-collections/intro-to-collection-runs), [P5](https://learning.postman.com/docs/getting-started/basics/syncing).

**Безпека й надійність.** Postman Vault підтримує секрети для запитів та скриптів. Local Vault зберігає секрети локально; Shared Vault має окрему модель доступу й застосовується в підтримуваних хмарних сценаріях. Документація також розрізняє умови доступності секретів у ручних запусках і CLI/запланованих запусках. Це підтверджує наявність механізму секретів, але не дає підстав оцінювати загальний рівень захищеності продукту числом. Джерела: [P7](https://learning.postman.com/docs/use/postman-vault/use-vault-secrets), [P6](https://learning.postman.com/docs/postman-cli/postman-cli-run-collection).

**Обмеження та компроміс.** У Collection Runner збереження великих тіл відповідей залежить від налаштувань і ресурсів локального середовища; за умов великих запусків офіційна інструкція рекомендує зменшення обсягу накопичуваних даних. Для окремих типів колекцій CLI діють протокольні обмеження. Взаємодія із хмарними функціями створює залежність від обраного режиму синхронізації, тоді як lightweight-клієнт усуває її ціною відсутності такої синхронізації. Джерела: [P2](https://learning.postman.com/docs/tests-and-scripts/running-collections/intro-to-collection-runs), [P6](https://learning.postman.com/docs/postman-cli/postman-cli-run-collection), [P1](https://learning.postman.com/docs/getting-started/basics/using-api-client).

### 1.3.2 Insomnia

**Призначення й архітектура.** Insomnia — відкритий кросплатформний API-клієнт. У документі розробників зазначено desktop-архітектуру на Electron/React з мережевими операціями через libcurl; це свідчення щодо реалізації **клієнта**, а не доказ мікросервісної чи монолітної організації сторонньої хмари. Описані режими Local Vault, Scratch Pad, Cloud Sync та Git Sync. Файл `DEVELOPMENT.md` містить історичні відомості про локальний NeDB, проте відповідність цієї деталі **всім актуальним збіркам** окремо не встановлено; тому NeDB не визначається тут як гарантована поточна СУБД продукту. Джерела: [I1](https://github.com/kong/insomnia), [I2](https://github.com/Kong/insomnia/blob/develop/DEVELOPMENT.md), [I3](https://developer.konghq.com/insomnia/storage/).

**Протоколи та HTTP-взаємодія.** Офіційний репозиторій вказує на REST/HTTP, GraphQL, gRPC, WebSocket та Server-Sent Events. Наявність цих клієнтських режимів не визначає протоколи, якими обмінюються внутрішні компоненти хмарного сервісу. Джерело: [I1](https://github.com/kong/insomnia).

**Сценарне виконання та перевірки.** Collection Runner виконує вибрані запити у визначеному порядку, підтримує ітерації. Pre-request та after-response scripts змінюють змінні, зчитують JSON/статус/час відповіді й формують перевірки; документовано response chaining. Для автоматизованого запуску колекцій передбачено Inso CLI з параметрами середовища, даних і таймауту. Джерела: [I6](https://developer.konghq.com/insomnia/scripts/), [I7](https://developer.konghq.com/insomnia/test/), [I8](https://developer.konghq.com/inso-cli/reference/run_collection/).

**Дані та результати.** Local Vault та Scratch Pad дозволяють локальну роботу; Cloud Sync забезпечує синхронізацію, а Git Sync зберігає ресурси у YAML-файлах Git-репозиторію, дотримуючись звичайних процедур комітів і конфліктів. Тип СУБД, модель транзакцій і протоколи внутрішньої хмарної інфраструктури в цих документах **не розкриті в обсязі, достатньому для технічного зіставлення**. Джерела: [I3](https://developer.konghq.com/insomnia/storage/), [I4](https://developer.konghq.com/insomnia/git-sync/).

**Безпека й надійність.** У приватних глобальних підсередовищах підтримуються зашифровані *secret variables* з ключем сховища. Водночас позначення звичайної змінної як *confidential* не означає її шифрування при експорті: документація прямо зазначає, що такі значення експортуються у відкритому вигляді. У Inso CLI можна встановити таймаут запиту. Джерела: [I5](https://developer.konghq.com/insomnia/environments/), [I8](https://developer.konghq.com/inso-cli/reference/run_collection/).

**Обмеження та компроміс.** За використання Git Sync зміни й конфлікти керуються Git, а під час деяких операцій у репозиторії може з’являтися додаткова службова метаінформація. Ризик розкриття *confidential values* під час експорту потребує застосування саме *secret variables*, а не лише відповідної позначки. Це перевірювані умови експлуатації, але не свідчення загальної небезпечності Insomnia. Джерела: [I4](https://developer.konghq.com/insomnia/git-sync/), [I5](https://developer.konghq.com/insomnia/environments/).

### 1.3.3 Bruno

**Призначення й архітектура.** Bruno — відкритий локальний API-клієнт з desktop-застосунком на Electron/React і CLI, що випливає з офіційної структури відкритого репозиторію. Колекції розміщуються у файловій системі з можливістю Git-версіювання. В актуальних версіях Bruno для нових колекцій за замовчуванням використовується формат OpenCollection YAML; формат `.bru` також підтримується. Існуючі колекції `.bru` можна продовжувати використовувати або окремо мігрувати до YAML. Джерела: [B1](https://github.com/usebruno/bruno), [B2](https://github.com/usebruno/bruno/blob/main/contributing.md), [B3](https://www.usebruno.com/opencollection), [B8](https://www.usebruno.com/changelog), [B9](https://blog.usebruno.com/making-yaml-the-default-in-bruno-v3.1).

**Протоколи та HTTP-взаємодія.** Документовано клієнтську підтримку REST/HTTP, GraphQL, gRPC та WebSocket. Для теми дипломного проєкту релевантним піднабором є HTTP-запити до REST API. Джерело: [B7](https://www.usebruno.com/product/api-client).

**Сценарне виконання та перевірки.** Bruno підтримує змінні середовища, скрипти та твердження (assertions). Через JavaScript API доступні дані відповіді й встановлення змінних наступних запитів. Команда `bru run` запускає колекції/папки, а CLI може формувати файли результатів JSON, JUnit та HTML. Наявність цих форматів засвідчує можливість експорту результатів, але не автоматично наявність централізованої історії запусків у СУБД. Джерела: [B4](https://github.com/usebruno/bruno/blob/main/packages/bruno-cli/readme.md), [B5](https://github.com/usebruno/bruno-docs/blob/main/testing/script/javascript-reference.mdx), [B7](https://www.usebruno.com/product/api-client).

**Дані та результати.** Файлова модель і Git-інтеграція роблять колекції доступними для diff і code review; Bruno не позиціонує хмарну синхронізацію як власну функцію. Відкритий репозиторій містить окремий пакет, названий `bruno-sqlite`, однак саме ця назва **не доводить**, що колекції або всі результати виконання зберігаються у SQLite. Документована модель зберігання колекцій — файлові формати OpenCollection YAML/`.bru`. Джерела: [B1](https://github.com/usebruno/bruno), [B2](https://github.com/usebruno/bruno/blob/main/contributing.md), [B3](https://www.usebruno.com/opencollection).

**Безпека й надійність.** Секретні змінні зберігаються локально, не потрапляють до файлів середовища; офіційно описано шифрування засобами операційної системи або резервний AES-256. CLI підтримує зупинення при збої (`--bail`) та опції перевірки сертифікатів. Це окремі механізми контролю, а не підтвердження певного значення Fault Tolerance або гарантій безпеки в умовах довільних навантажень. Джерела: [B6](https://github.com/usebruno/bruno-docs/blob/main/secrets-management/secret-variables.mdx), [B4](https://github.com/usebruno/bruno/blob/main/packages/bruno-cli/readme.md).

**Обмеження та компроміс.** Відсутність власної хмарної синхронізації є **свідомим вибором моделі**; для командного обміну артефактами необхідний Git або інша зовнішня система. Файлове представлення підтримує простежуваність змін колекцій, проте не є готовою прикладною моделлю збереження історії тестових запусків і запитів вебзастосунку. Друге твердження є **інженерним висновком про відмінність цілей продуктів**, а не виміряним дефектом Bruno. Джерела: [B1](https://github.com/usebruno/bruno), [B3](https://www.usebruno.com/opencollection), [B4](https://github.com/usebruno/bruno/blob/main/packages/bruno-cli/readme.md).

### 1.3.5 Аналітичний висновок підрозділу 1.3

Проведене порівняння показує, що досліджені аналоги застосовують різні способи організації тестових артефактів і сценарного виконання. Postman поєднує колекції зі сценарними скриптами та локальними/хмарними режимами; Insomnia підтримує виконання колекцій поряд із вибором локального, Git- або хмарного зберігання; Bruno використовує Git-орієнтовану файлову модель з окремим CLI. Виявлені компроміси стосуються, зокрема, меж синхронізації, експорту секретів і збереження результатів. Документовані можливості цих продуктів підтверджують доцільність моделі впорядкованих HTTP-кроків, спільного контексту змінних та явно сформульованих правил перевірки; вони не підтверджують універсальної переваги будь-якого з рішень за швидкодією чи захищеністю.

Для кваліфікаційного проєкту обрано C#/.NET, ASP.NET Core, Blazor, Entity Framework Core та PostgreSQL із модульною монолітною архітектурою. За визначеного обсягу реалізації цей підхід дозволяє розмежувати керування сценаріями, HTTP-виконання, перевірки відповідей та збереження історії в межах одного застосунку без додаткових мережевих меж між модулями. `HttpClient` і `async/await` застосовуватимуться для контрольованих HTTP-операцій, а PostgreSQL — для відтворюваної прив'язки результатів до запусків, кроків та правил перевірки. Така архітектура є **обґрунтовано достатньою для сформульованих вимог**, але її ефективність і безпека мають підтверджуватися майбутніми тестами, а не припускатися апріорі.

Інженерну цінність запланованого рішення визначає не розширення переліку протоколів або повторення універсального API-клієнта, а керований механізм виконання залежних REST API-запитів за схемою «запит → отримання значення JSON → підстановка у наступний крок → перевірки → збереження результатів → звіт». Навмисне обмеження простими шляхами до JSON-властивостей, послідовним порядком та фіксованими видами перевірок зменшує складність реалізації й полегшує перевірку коректності. Наступний розділ проєктування має визначити межі програмних модулів, модель даних сценарію й запуску та алгоритм передавання значень між кроками без розширення п'яти затверджених Core Features.

## 1.4. Аналіз обраної предметної області в межах дослідження (модель As-Is)

### 1.4.1. Загальна характеристика домену, актори та інформаційні сутності

Предметною областю є перевірка поведінки REST API за заздалегідь визначеними HTTP-сценаріями. Операції API пов'язують клієнтську й серверну частини інформаційної системи, а їх перевірка охоплює семантику HTTP-статусів, значення структурованих JSON-відповідей, тривалість запитів і реакцію на помилки. Для залежних операцій важлива не тільки коректність окремого запиту, а й збереження даних між послідовними кроками та можливість повторити той самий набір перевірок після зміни реалізації API.

**Основний актор** — розробник або QA-інженер, який задає очікувані результати, запускає сценарії та аналізує відхилення. **Зовнішній учасник взаємодії** — тестований REST API, що приймає запити й повертає статус, заголовки та, за наявності, тіло відповіді. Окремий адміністратор, складна модель ролей і багатокористувацьке узгодження результатів у межі проєкту не включені.

**Основні інформаційні сутності:** тестовий сценарій (впорядкована сукупність кроків); крок сценарію (позиція, конфігурація HTTP-запиту та перевірки); HTTP-запит (метод, адреса, заголовки, параметри й тіло); змінна сценарію (іменоване значення, отримане під час конкретного запуску); правило перевірки (очікувані HTTP-статус, JSON-значення або обмеження часу); запуск сценарію (ідентифікатор, дата, стан, тривалість); результат кроку та перевірки (факт проходження або діагностика помилки). Концептуально конфігурація сценарію відділяється від історичних результатів запуску; конкретна модель таблиць визначатиметься у Розділі 2.

### 1.4.2. Типовий робочий процес As-Is

Модель As-Is характеризує **обраний ручний процес роботи з окремими HTTP-запитами**, а не всі сучасні API-клієнти. Postman, Insomnia та Bruno вже підтримують низку механізмів автоматизації; ці можливості предметно наведено у підрозділі 1.3. Вузькі місця виникають за відсутності налаштованого сценарного виконання, а не внаслідок принципової неспроможності названих продуктів.

**Процес 1 — ручне створення та повторне виконання послідовності HTTP-запитів.** Початкові дані: адреси API, методи `POST` і `GET`, заголовки, тіло запиту, очікувані статуси й доступ до тестового середовища. Фахівець формує перший запит, надсилає його, перевіряє відповідь, відкриває або редагує наступний запит і повторює операції під час наступного проходу. Залучені сутності: HTTP-запит, крок сценарію, відповідь, очікуваний результат. Результатом є набір окремих спостережень про відповіді. Вузьке місце — ручне повторення порядку операцій та параметрів. Пропуск кроку, неузгоджені вхідні дані або зміна тестового оточення погіршують відтворюваність; ці ризики не означають, що конкретний API-клієнт не підтримує колекцій.

**Процес 2 — передавання значення між залежними викликами.** Початкові дані: JSON-відповідь `POST`, яка містить `data.id`, та шаблон адреси `GET /resources/{id}`. Після надсилання `POST` фахівець знаходить потрібне поле, копіює ідентифікатор, підставляє його до наступного URL і відправляє `GET`. Залучені сутності: JSON-відповідь, змінна сценарію, параметри HTTP-запиту. Результат — запит до створеного ресурсу. Вузьке місце — ручне вилучення та підстановка значення: копіювання старого ідентифікатора, помилки в шляху до поля або відсутність поля не завжди виявляються до наступного запиту. Для повторного запуску інший ідентифікатор потребує нової операції; у сучасних інструментах цей крок може бути автоматизований скриптами або змінними.

**Процес 3 — перевірка відповіді та документування проходження.** Початкові дані: очікуваний HTTP-статус, значення JSON-поля, поріг часу відповіді та фактичні відповіді. Фахівець зіставляє результати з очікуваннями, заносить підсумок у нотатки або таблицю, а при повторних перевірках зіставляє записи вручну. Залучені сутності: правило перевірки, результат кроку, запуск сценарію, журнал перевірок. Результат — документоване рішення щодо проходження тесту. Вузьке місце — неоднаковий формат записів, неповна прив'язка до конкретного запуску та пропуск окремої перевірки. Без формалізованої історії важко відділити проблему API від невиконаного кроку або помилки даних; при цьому окремі аналоги вже надають звіти про запуски.

### 1.4.3. Потоки даних і застосовні технологічні обмеження

Типовий потік даних має вигляд: конфігурація HTTP-кроку → зовнішній REST API → HTTP-відповідь → вилучення JSON-поля → параметри наступного кроку → перевірки → запис результату. У ручному As-Is контекст змінних і журнал результатів можуть існувати лише як неформалізовані дії фахівця. У проєктованій системі цей потік потрібно зробити явним і простежуваним. Для перевірки правильності HTTP і JSON релевантними специфікаціями є RFC 9110 та RFC 8259 [H1, H2].

Оскільки застосунок виконуватиме запити до адрес, заданих користувачем, передбачаються обмеження за дозволеними призначеннями, фактичними IP-адресами з'єднання й автоматичними перенаправленнями для зниження ризику SSRF [S1, S2]. Необхідні також обмеження на кількість кроків, розмір відповіді, час окремого HTTP-виклику та тривалість цілого сценарію, щоби помилка зовнішнього сервісу не спричинила неконтрольованого очікування або споживання ресурсів. Секретні заголовки та змінні не повинні потрапляти у відкритому вигляді до історії й діагностичних повідомлень; при збереженні результатів необхідно мінімізувати обсяг тіла відповіді. Вимоги GDPR, ISO, OAuth2/OIDC чи окремої рольової моделі не встановлюються безумовними: їх застосовність залежить від фактичних даних, середовища розгортання і правил експлуатації.

## 1.5. Постановка задачі та формування вимог (модель To-Be, Core Features, NFRs)

### 1.5.1. Цільова модель To-Be

Модель To-Be передбачає один вебзастосунок з модульною монолітною архітектурою. Користувач у Blazor створює сценарій, налаштовує HTTP-кроки у фіксованому порядку, визначає очікувані статуси, значення JSON та часові пороги. Конфігурацію зберігає серверна частина ASP.NET Core через Entity Framework Core та PostgreSQL. Це усуває необхідність щоразу відтворювати порядок операцій вручну, водночас не вимагає підтримки довільних скриптів або багатокористувацького виконання.

Під час запуску сервер послідовно виконує HTTP-запити через `HttpClient`, підтримуючи іменований контекст **лише поточного запуску**. Значення з JSON-відповіді за шляхом на зразок `data.id` потрапляє до цього контексту і підставляється в параметри наступного кроку. За відсутності значення або помилки HTTP застосовується визначена діагностика без неконтрольованого переходу до залежного запиту. Цей механізм безпосередньо відповідає другому вузькому місцю As-Is — ручному перенесенню ідентифікатора.

На кожному кроці окремий модуль перевірок зіставляє HTTP-статус, JSON-поле та фактичну тривалість відповіді із встановленими критеріями. Модуль збереження фіксує запуск і його результати без необмеженого накопичення тіл HTTP-відповідей та секретів. Вебінтерфейс відображає кількість пройдених/непройдених перевірок і деталізацію окремого запуску. Таким чином третє вузьке місце As-Is — розрізнене документування — замінюється зв'язною історією, придатною для аналізу причин відхилень.

**Матриця переходу As-Is → To-Be:**

| Проблема As-Is | Передбачений механізм | Очікувана зміна процесу | Майбутній спосіб перевірки |
| --- | --- | --- | --- |
| Ручне повторення послідовності HTTP-запитів | Збережений сценарій з упорядкованими кроками | Повторне виконання без ручного відтворення порядку | Контрольний сервер фіксує порядок трьох запитів у двох запусках |
| Копіювання `data.id` між `POST` і `GET` | JSON-вилучення та іменовані змінні запуску | Наступний запит отримує поточне значення автоматично | Інтеграційний тест `POST → GET` із різними ID |
| Розрізнені нотатки та перевірки | Assertions, PostgreSQL-історія та звіт | Результати зіставляються з конкретним запуском і кроком | Порівняння звіту й записів БД для успіху та помилки |

### 1.5.2. Функціональні вимоги

У межах актуального Thesis Proposal визначено **п’ять функціональних груп (Core Features)**. Наведені нижче вісім вимог FR деталізують їх без додавання нових функціональних напрямів. Для всіх FR поточний статус — **заплановано**, оскільки програмна реалізація на цьому етапі не підтверджена.

- **FR-01 (Керування сценаріями та запитами).** Створювати, редагувати й видаляти тестові сценарії з упорядкованими кроками. **Перевірка:** Зберегти сценарій, змінити порядок двох кроків, повторно відкрити та видалити його.
- **FR-02 (Керування сценаріями та запитами).** Налаштовувати для кроку HTTP-метод GET/POST/PUT/PATCH/DELETE, URL, заголовки, параметри й тіло. **Перевірка:** Зберегти та відновити п’ять методів і варіанти параметрів.
- **FR-03 (Автоматизоване сценарне виконання).** Виконувати кроки сценарію у визначеному порядку через асинхронні HTTP-запити. **Перевірка:** Контрольний сервер реєструє порядок із трьох викликів.
- **FR-04 (Автоматизоване сценарне виконання).** Вилучати значення за простим шляхом JSON-властивості та підставляти іменовані змінні до наступних запитів. **Перевірка:** POST повертає `data.id`; GET використовує відповідне значення; відсутнє поле обробляється як помилка.
- **FR-05 (Перевірка результатів HTTP-запитів).** Порівнювати фактичні HTTP-статус, вибране JSON-поле й час відповіді з визначеними правилами. **Перевірка:** Для кожного типу правила перевірити позитивний та негативний випадки.
- **FR-06 (Збереження історії тестування).** Зберігати запуск, часові позначки, підсумковий стан, тривалість, результати кроків та перевірок. **Перевірка:** Після перезапуску застосунку відкрити запис конкретного запуску з деталями.
- **FR-07 (Аналіз результатів і формування звітів).** Відображати у вебінтерфейсі список запусків із підсумковими станами і кількістю успішних та невдалих перевірок. **Перевірка:** Для контрольного запуску зі змішаними результатами перевірити підрахунки в інтерфейсі.
- **FR-08 (Аналіз результатів і формування звітів).** Відображати деталізований звіт конкретного запуску з порядком кроків, результатами перевірок і причинами помилок. **Перевірка:** Відкрити звіт за ID та звірити його з даними PostgreSQL.

### 1.5.3. Нефункціональні вимоги та критерії приймання

Наведені метрики є **проєктними цілями для майбутнього приймання**, а не виміряними показниками реалізованого продукту. Для порівнянності вимірювань встановлено контрольний локальний стенд та явно розділено три часові поняття: відгук **власного вебзастосунку**, тривалість **цілого сценарію** і затримку **зовнішнього REST API**. Затримка зовнішнього сервісу не інтерпретується як швидкодія Blazor/ASP.NET Core. Обрано помірний рівень навантаження, відповідний навчально-практичному прототипу, без потреби доводити стійкість до тисяч користувачів.

**Обґрунтування граничних значень.** Порогові 5 HTTP-запитів/с і p95 ≤ 800 мс стосуються лише локальних операцій перегляду власного застосунку й перевіряються без зовнішнього API. Межі 20 кроків, 10 с на крок, 60 с на запуск, 1 MiB відповіді та два одночасні запуски запобігають неконтрольованому використанню ресурсів однієї інстанції; це стартові критерії, які можуть переглядатися за обґрунтованими експериментами. Для NFR-02 контрольована затримка API задана явно, щоб перевіряти додаткові витрати механізму, а не випадкову поведінку мережі. Результати приймальних і навантажувальних випробувань до реалізації відсутні.

**Межі безпеки.** Запобігання SSRF передбачає дозволені HTTPS-призначення й контроль кінцевої адреси мережевого з'єднання, а не лише синтаксичну перевірку URL. Довірений локальний API може використовуватися у відокремленому профілі для інтеграційних тестів. Секретні значення з конфігурації середовища застосовуються під час формування HTTP-запиту, але не повинні записуватися в історію та логи; зберігаються лише безпечні метадані. Ці обмеження потребуватимуть негативних тестів і не означають повного доведеного захисту до реалізації.

### 1.5.4. Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка системи автоматизованого сценарного тестування REST API з аналізом результатів на основі модульної монолітної архітектури C#/.NET, ASP.NET Core, Blazor, Entity Framework Core та PostgreSQL для відтворюваного виконання послідовностей взаємозалежних HTTP-запитів, передавання значень JSON між кроками, формалізованої перевірки HTTP-статусів, JSON-полів і тривалості відповіді, збереження історії запусків та подання деталізованих звітів у вебінтерфейсі. Реалізація повинна врахувати перевірювані обмеження продуктивності, тривалості сценаріїв, паралельного виконання, захисту вихідних HTTP-запитів і секретів, цілісності даних та автоматизованого тестування. Ефективність і коректність запланованих механізмів підлягатимуть підтвердженню під час розроблення та випробувань.

## Висновки до розділу 1

У першому розділі проаналізовано інженерні особливості сценарного тестування REST API: формування впорядкованих HTTP-запитів, передавання значень між залежними операціями, перевірку статусів і JSON-відповідей та простежуване накопичення результатів. Встановлено, що у вибраному ручному процесі As-Is основними вузькими місцями є багаторазове відтворення послідовності кроків, ручне перенесення отриманих значень і роз'єднане документування результатів. Ці недоліки стосуються визначеного способу організації роботи, а не всіх програмних засобів тестування API.

Порівняння Postman, Insomnia та Bruno за шістьма технічними критеріями підтвердило наявність у промислових інструментах засобів сценарного запуску, змінних, перевірок та різних режимів зберігання артефактів. Одночасно встановлено відмінності їхніх підходів до локальної роботи, синхронізації, командного виконання та поводження із секретами. Здійснене порівняння не містить спільного вимірювального експерименту, тому не дає підстав стверджувати перевагу майбутньої системи за швидкодією, захищеністю або функціональною повнотою. Воно визначає інженерні межі, у яких доцільно реалізувати керований механізм перевірок із постійною історією запусків.

Для поставленої задачі обґрунтовано модульну монолітну архітектуру: серверні компоненти керування сценаріями, HTTP-виконання, верифікації й збереження даних можуть розмежовувати відповідальність у межах одного застосунку ASP.NET Core з інтерфейсом Blazor. Використання `HttpClient`, Entity Framework Core та PostgreSQL відповідає п'яти визначеним Core Features без запровадження брокерів, мікросервісів, складної рольової моделі чи недоведеної вимоги до горизонтального масштабування. Сформовано вісім атомарних функціональних вимог та дев'ять NFR із критеріями й методами перевірки; їх виконання ще не підтверджено експериментально.

Подальше дослідження спрямовується на деталізацію контрактів між модулями, моделі даних і алгоритмів збереження контексту змінних, обробки помилок, контролю адрес та перевірки результатів. У Розділі 2 необхідно спроєктувати структуру компонентів, сутності сценаріїв і запусків та зв'язки між ними, а у Розділі 3 — реалізувати й випробувати функціональність, перевірити обрані NFR у контрольованих умовах та задокументувати фактичні результати. Отже, сформована аналітична база визначає межі реалізації й критерії подальшої інженерної перевірки, але не замінює такої перевірки.
